For A4 we added a PostgreSQL database to QueueSmart. Everything the app uses is now saved in the database: accounts, profiles, places, services, queues, tickets and notifications. If the server restarts, nothing is lost.

The tables are defined in backend/db/schema.sql. The code that talks to the database is in backend/src (db.js and the *Repo.js files), and the tests are in backend/tests.

docker compose up -d     # starts the database, back end and front end
cd backend
npm install
npm test                 # runs the tests
npm run coverage         # runs the tests and shows coverage

Why PostgreSQL? Our data is connected: a place has services, each service has a queue, and each queue has tickets from users. A relational database fits this well. Foreign keys keep the links correct, and constraints stop bad data from being saved. It also fit our earlier work. In A3 all data went through one file, so we could replace it with database code without changing the API or the A2 screens.

A few small differences from the assignment:

  • A queue can also be Paused, not only Open or Closed, because our A2 admin screens already have a pause option.
  • Instead of one "canceled" status, a ticket can be left, removed or no-show, so history shows why the ticket ended.
  • When an admin deletes a service, we only mark it as deleted. This way users can still see their old tickets in history.

SQL to create the tables (backend/db/schema.sql)

-- QueueSmart database schema (PostgreSQL). Matches schema.dbml, plus the rules
-- DBML can't express: CHECK constraints and partial unique indexes.
-- Docker runs this file the first time the database volume is created.

CREATE TYPE user_role AS ENUM ('user', 'admin');
CREATE TYPE priority_level AS ENUM ('Low', 'Normal', 'High');
CREATE TYPE queue_status AS ENUM ('Open', 'Paused', 'Closed');
CREATE TYPE entry_status AS ENUM ('waiting', 'serving', 'served', 'left', 'removed', 'no-show');
CREATE TYPE notification_type AS ENUM ('Queue update', 'Status change');
CREATE TYPE notification_status AS ENUM ('sent', 'viewed');

CREATE TABLE place (
  id integer PRIMARY KEY, -- 6-digit id, also the join code
  name varchar(50) NOT NULL
);

CREATE TABLE user_credentials (
  id integer PRIMARY KEY, -- 6-digit id from the app
  email varchar(254) NOT NULL UNIQUE,
  password_hash varchar(255) NOT NULL, -- scrypt salt:hash, never plain text
  role user_role NOT NULL DEFAULT 'user',
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE user_profile (
  user_id integer PRIMARY KEY REFERENCES user_credentials (id),
  email varchar(254) NOT NULL UNIQUE REFERENCES user_credentials (email) ON UPDATE CASCADE,
  first_name varchar(50) NOT NULL,
  last_name varchar(50) NOT NULL,
  phone varchar(20),
  email_me boolean NOT NULL DEFAULT true,
  place_id integer REFERENCES place (id) -- admins only: the place they run
);

CREATE TABLE service (
  id integer PRIMARY KEY,
  place_id integer NOT NULL REFERENCES place (id),
  name varchar(100) NOT NULL,
  description varchar(500) NOT NULL,
  duration integer NOT NULL CHECK (duration BETWEEN 1 AND 480), -- minutes
  priority priority_level NOT NULL,
  max_in_line integer NOT NULL DEFAULT 25 CHECK (max_in_line BETWEEN 1 AND 500),
  opens time NOT NULL DEFAULT '09:00',
  closes time NOT NULL DEFAULT '16:30',
  appointments boolean NOT NULL DEFAULT false,
  deleted_at timestamptz, -- keeps ticket history after a delete
  CHECK (closes > opens)
);

CREATE INDEX service_place_id_idx ON service (place_id);

CREATE TABLE queue (
  id integer PRIMARY KEY,
  service_id integer NOT NULL UNIQUE REFERENCES service (id),
  status queue_status NOT NULL DEFAULT 'Closed',
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE queue_entry (
  id integer PRIMARY KEY,
  queue_id integer NOT NULL REFERENCES queue (id),
  user_id integer NOT NULL REFERENCES user_credentials (id),
  ticket varchar(12) NOT NULL, -- e.g. A-001
  service_name varchar(100) NOT NULL, -- name at time of joining
  priority priority_level NOT NULL DEFAULT 'Normal',
  position integer NOT NULL, -- queueOrder in the code
  status entry_status NOT NULL DEFAULT 'waiting',
  joined_at timestamptz NOT NULL DEFAULT now(),
  started_at timestamptz,
  completed_at timestamptz,
  close_notified boolean NOT NULL DEFAULT false
);

CREATE INDEX queue_entry_queue_status_idx ON queue_entry (queue_id, status);
CREATE INDEX queue_entry_user_status_idx ON queue_entry (user_id, status);

-- A user can only have one active ticket at a time
CREATE UNIQUE INDEX one_active_ticket_per_user ON queue_entry (user_id)
  WHERE status IN ('waiting', 'serving');

-- A queue can only serve one person at a time
CREATE UNIQUE INDEX one_serving_per_queue ON queue_entry (queue_id)
  WHERE status = 'serving';

CREATE TABLE notification (
  id integer PRIMARY KEY,
  user_id integer NOT NULL REFERENCES user_credentials (id),
  type notification_type NOT NULL,
  message varchar(255) NOT NULL,
  status notification_status NOT NULL DEFAULT 'sent',
  emailed boolean NOT NULL DEFAULT false,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX notification_user_id_idx ON notification (user_id);

CREATE TABLE saved_place (
  user_id integer REFERENCES user_credentials (id),
  place_id integer REFERENCES place (id),
  PRIMARY KEY (user_id, place_id)
);

CREATE TABLE session (
  token uuid PRIMARY KEY,
  user_id integer NOT NULL REFERENCES user_credentials (id),
  created_at timestamptz NOT NULL DEFAULT now()
);

3. Validation and Saving Data

We check the data in two places. First, the back end checks every request and sends back a clear error message. Then the database checks it again, so bad data can't be saved even if something gets past the back end.

RuleBack endDatabase
Required fieldsReturns "… is required."NOT NULL
Length limitsFor example: names 50, email 254, description 500 charactersvarchar with the same limits
Data typesNumbers, true/false, times and allowed valuesColumn types, enums and CHECK rules
Unique valuesA duplicate email returns an errorUNIQUE email, and only one active ticket per user

All forms in the app send their data to the back end, which saves it in the database. The screens, like queue status, history, services, notifications and profile, load their data from the database. To test this, we restarted the server, and all the data was still there.
